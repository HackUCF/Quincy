# config

Stores and provides access to the API configuration for the rest of the server. Configuration is loaded by the CLI layer (via viper) and passed in through a setter; this package does not read files directly. The config describes the full competition setup: number of teams, boxes with host address templates, services on each box with their check assignments and optional userlist references, credential userlists with optional domain and NetBIOS settings, the HTTP listener address and port, and an optional sinks section that configures data backends.

Two sinks are currently supported. The PostgreSQL sink enables persistent score storage and all database-backed routes. The OpenTelemetry sink ships each score result as an OTLP log record to a configurable HTTP endpoint; it supports HTTP Basic auth (either as a username/password pair or a pre-encoded credential string), a vendor-specific stream routing header, and tunable batching parameters with sensible defaults. Both sinks are optional and independently enabled by the presence of their respective configuration blocks.

The sinks type exposes helper methods consumed at router setup time. These allow individual routes to be conditionally swapped at startup: routes that require a database can be replaced with a 501 Not Implemented handler, and database-specific middleware can be turned into a no-op, all without any per-request branching.

The package follows the same middleware pattern used by the database connection layer. A Gin middleware stores the config object in each request's context at startup, and a pair of context-based accessors allow handlers to retrieve it — one that panics on error and one that returns an error explicitly. The setter that stores the config guards against being called more than once by panicking on a second invocation. The default config YAML is embedded in the binary at build time and exposed so the CLI layer can write it to disk. Validation logic is currently stubbed out.

Environment variables can override any config field using the prefix `QU_` followed by the field path with dots and hyphens replaced by underscores (e.g. `QU_SINKS_POSTGRES_PASSWORD`, `QU_SINKS_OTEL_BASIC_AUTH`).
